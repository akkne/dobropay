# Правила проекта (AGENTS.md)

Этот файл — обязательная точка входа для каждого агента при работе с репозиторием **Dobropay**.

## 1. Обязательное чтение перед началом работы

Перед проектированием, написанием кода или выполнением любых команд обязательно прочитай:
1. Корневой обзор: [README.md](README.md)
2. Карту документации: [docs/README.md](docs/README.md)
3. Стандарты написания кода (Code Style): [docs/code-style.md](docs/code-style.md)
4. Правила работы с Git: [docs/git-process.md](docs/git-process.md)
5. Архитектуру и ТЗ: [docs/architecture/architecture.md](docs/architecture/architecture.md) и [docs/architecture.md](docs/architecture.md)

Прямые указания владельца репозитория имеют приоритет над путями в старых документах: весь серверный код находится в каталоге `backend/`.

## 2. Осмотр репозитория

Перед проектированием или правкой осмотри весь репозиторий:
- Проверь `git status --short --branch`, staged, unstaged и untracked файлы.
- Изучи дерево `backend/`, `frontend/`, `docs/`, `tests/`, `infra/`, `compose.yaml`, `.env.example`, `Dobropay.slnx` и существующие контракты.
- Не выбирай новую структуру по одному файлу и не игнорируй соседние каталоги.

## 3. Целевая архитектура: Microservices & DB-per-Service

- Архитектура проекта — **независимые микросервисы с паттерном Database-per-Service (отдельный контейнер PostgreSQL на каждый сервис со своей БД)**, а не модульный монолит и не общая БД для микросервисов.
- Сервисы с собственными физически изолированными экземплярами БД:
  - `Dobropay.Auth` → `auth-db` (`auth_db`)
  - `Dobropay.DeveloperApi` → `merchant-dev-db` (`merchant_dev_db`)
  - `Dobropay.Payments` → `payments-db` (`payments_db`)
  - `Dobropay.Notifications` → `notifications-db` (`notifications_db`, плюс `redis`)
  - `Dobropay.Receipts` → `receipts-db` (`receipts_db`)
- Сервисы без собственной БД: `Dobropay.MerchantAdmin`, `Dobropay.Email`, `gateway` (Caddy).
- Межсервисное взаимодействие строится строго через синхронные внутренние HTTP API и асинхронную шину событий **Kafka** (`Dobropay.Messaging` / `Dobropay.Contracts`). Никакой сервис не имеет права подключаться к чужой БД.

## 4. Требования к коду (Code Style & Clean Code)

Подробные правила зафиксированы в [docs/code-style.md](docs/code-style.md). Ключевые принципы:
- **Никаких ИИ-артефактов**: чистый, лаконичный, идиоматичный C#-код без лишних комментариев, шаблонных приписок и мусора.
- **Один класс — один файл**: каждый `class`, `interface`, `record` или `enum` обязан находиться в собственном файле, имя которого строго совпадает с именем типа.
- **Сначала абстракция, потом реализация**: проектируй через интерфейсы (`Interfaces` / `Abstractions`) и внедрение зависимостей (DI), затем пиши конкретные классы реализации. Везде строгое ООП и соблюдение SOLID.
- **Никаких магических строк и чисел**: все маршруты (slugs), названия заголовков, кук, топиков, ролей, статусов, SQL-константы и ключи конфигурации выносятся в отдельные статические классы констант или типизированные `Options`.
- **Все переменные окружения и секреты — в `.env`**: в коде и `appsettings.json` не должно быть захардкоженных строк подключения, паролей, ключей, URL или портов. Все значения приходят из `.env` (шаблон — в `.env.example`) и маппятся в типизированные настройки.
- **Чистое взаимодействие с БД и инфраструктурой**: подключение к PostgreSQL, Kafka, Redis и HTTP-клиентам реализуется через абстракции, фабрики/провайдеры соединений, репозитории и управляемые DI-сервисы.

## 5. Правила работы с Git и чистота рабочего дерева

Подробный регламент находится в [docs/git-process.md](docs/git-process.md):
- Всегда работай в ветке фичи (не коммить напрямую в `main`).
- Делай небольшие атомарные коммиты по стандарту Conventional Commits (`feat`, `fix`, `refactor`, `test`, `docs`, `chore`) по мере завершения логического блока и сразу пушь ветку (`git push`).
- Автор и коммиттер — исключительно владелец репозитория (`git config user.name` / `git config user.email`). Запрещены `Co-Authored-By`, трейлеры и подписи инструментов/ИИ.
- Сохраняй чужие изменения рабочего дерева и индекса, если не поручено иное. Перед коммитом проверяй `git diff --cached` на отсутствие секретов.
- **После завершения работы агента в репозитории не должно оставаться никаких лишних, временных, неотслеживаемых файлов или артефактов.** Рабочее дерево должно быть чистым (`git status --short`), проект должен собираться без предупреждений (`dotnet build Dobropay.slnx -warnaserror`), а все тесты — проходить (`dotnet test Dobropay.slnx --no-build`).
