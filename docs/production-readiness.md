# Подготовка к выпуску

## Выполнено

- Удалены локальные данные кабинета и старые статические страницы с имитацией операций. Ошибки API больше не превращаются в успешные платежи, возвраты или ключи в браузере.
- `Dobropay.Setup` применяет миграции пяти изолированных баз без создания демонстрационных аккаунтов, магазинов, API-ключей и webhook-подписок.
- При выключенной песочнице `Dobropay.Payments` блокирует изменяющие запросы и отдаёт `503` на `/health/ready`. Создание магазина не выпускает тестовый ключ.
- Убран локальный SMTP-приёмник из Compose. Почта требует внешний SMTP с аутентификацией и TLS. Миграция `RemoveDemoReceipts` удаляет таблицу демонстрационных квитанций вместе с её данными; перед применением к существующей базе нужна резервная копия.
- Убраны прямые маршруты симуляции checkout и локального webhook-приёмника из gateway; при выключенной песочнице Payments блокирует также варианты через `/v1/checkout/*`.

## До запуска приёма денег

1. Реализовать и испытать адаптеры реального эквайринга для карт и СБП: создание попытки, подтверждение от провайдера, сверка неизвестных исходов, capture, cancel и refund. Существующие `BankCardPaymentProvider`, `SbpPaymentProvider` и `CryptoPaymentProvider` сейчас возвращают синтетические идентификаторы и результаты. После подключения снять блокировку изменяющих запросов и добавить проверку готовности провайдера.
2. Согласовать фактический API облачной кассы с `CloudKktFiscalProvider`, проверить реквизиты, сбои, повторную отправку и доставку чеков. Текущий клиент использует общий HTTP-контракт без подтверждённой интеграции с конкретным оператором.
3. Подключить внешний SMTP и проверить доставку. Настроить защищённый публичный интерфейс подписки webhook: внутренний маршрут Notifications есть, но кабинет пока показывает только журнал доставок.
4. Подготовить инфраструктуру выпуска: отказоустойчивый Kafka, резервные копии каждой БД, мониторинг, управление секретами, TLS-домен и проверка сетевой изоляции. Compose с одним брокером предназначен для развертывания и проверки компонентов, а не для отказоустойчивого приёма денег.
5. Провести интеграционную проверку реальными учётными данными партнёров, оценку безопасности платёжной формы и юридическую проверку фискализации.

Файл `.env.example` содержит только имена параметров. Значения и секреты в репозиторий не коммитятся. Другие уже сохранённые демонстрационные аккаунты и платежи миграция не удаляет; при переходе с локального контура их нужно проверить и удалить по утверждённой процедуре работы с данными.
