# Задание агенту — инициализация микросервисов Dobropay

Подготовь репозиторий Dobropay, реализуй минимальный сквозной сценарий в локальной песочнице и напиши документацию по фактической реализации. Каждый из семи сервисов ниже запускается отдельно. Kafka, Redis и все пять отдельных PostgreSQL-инстансов (по паттерну Database-per-Service) входят в обязательный локальный контур. При наличии файла `dobropay-architecture.md` используй его как справочник. Это задание можно выполнить и без него.

## 1. Исходные условия и объём

Dobropay — шлюз оплаты для интернет-магазинов. Магазин создаёт платёж через API, покупатель платит у внешнего провайдера, Dobropay подтверждает результат и доставляет магазину уведомление. Локальная интеграция использует симулятор провайдера и синтетические данные.

Прочитай инструкции репозитория (`AGENTS.md`, `docs/code-style.md`, `docs/git-process.md`), проверь рабочие изменения, существующие сервисы, контракты и конфигурацию. Сохрани совместимые решения. Используй C#, .NET 10, ASP.NET Core, PostgreSQL, EF Core/Npgsql и Docker Compose. Серверные проекты располагаются в `backend/`, каждый из них имеет свой образ, процесс, настройки и собственный изолированный экземпляр базы данных (DB-per-Service). Фоновые обработчики запускаются в сервисах, которым принадлежат операции.

В текущую задачу входят инициализация инфраструктуры и один сценарий оплаты RUB в песочнице. Возвраты, реальные провайдеры, полноценная фискализация, СБП и криптовалюта описываются в дорожной карте. Модель денег на старте предполагает, что ими занимается провайдер. Собственные балансы магазинов, выплаты и сплитование потребуют отдельного проектирования.

## 2. Сервисы

| Проект / Compose-сервис | Ответственность | Хранилище и вызовы |
| --- | --- | --- |
| `Dobropay.Auth` / `auth` | Вход сотрудников, аккаунты, сессии и токены. | Отдельный инстанс БД `auth-db` (`auth_db`). Предоставляет проверяемую идентичность для Developer API и Merchant Admin API. |
| `Dobropay.DeveloperApi` / `developer-api` | Регистрация бизнеса, магазин, членство сотрудников, ключи API, настройки интеграции. | Отдельный инстанс БД `merchant-dev-db` (`merchant_dev_db`). Проверяет ключ по внутреннему маршруту для Payments. В настройках webhook делегирует запись сервису Notifications. |
| `Dobropay.Payments` / `payments` | Сервис магазинов и платежей с исходной схемы. Создание и чтение платежей, гостевой checkout, адаптер провайдера, серверное подтверждение, статусы. | Отдельный инстанс БД `payments-db` (`payments_db`). Проверка ключа через Developer API. Публикация и потребление событий через Kafka. |
| `Dobropay.MerchantAdmin` / `merchant-admin` | Кабинет магазина и API для просмотра списка и деталей платежей. | Без собственной БД. Проверяет личность и членство. Читает состояние из Payments, Notifications и Receipts через внутренний API с проверенным контекстом магазина. |
| `Dobropay.Notifications` / `notifications` | Подписки магазинов, подпись webhook, доставка, история и повторы. | Отдельный инстанс БД `notifications-db` (`notifications_db`), Redis для TTL-лимитов, Kafka consumer. |
| `Dobropay.Receipts` / `receipts` | Запись о чеке или квитанции, состояние и задание на отправку. Локальный документ явно маркируется как демонстрационный. | Отдельный инстанс БД `receipts-db` (`receipts_db`), Kafka consumer, вызов Email через внутренний API. |
| `Dobropay.Email` / `email` | Отправка переданного сообщения через SMTP. | Без собственной БД. SMTP-приёмник в Compose. Результат отправки записывает Receipts. |

Серверные проекты находятся в `backend/`, тесты в `tests/`, конфигурация запуска в `infra/`, документация в `docs/`, корневые `compose.yaml`, `.env.example` и `README.md`. В общие библиотеки (`Dobropay.Contracts`, `Dobropay.Messaging`) выносятся версионируемые транспортные контракты, константы и чистые абстракции инфраструктуры. Владельцы таблиц и бизнес-логика остаются внутри сервисов.

## 3. Вся инфраструктура

- **Gateway.** Разведи публичные маршруты аутентификации, dev-панели, API магазина, checkout, кабинета и webhook провайдера. Внутренние маршруты и хранилища доступны только по приватной сети. Внутренние HTTP-вызовы проверяют сервисную идентичность. Прописывай аутентификацию и передавай проверенный контекст магазина между сервисами. Клиентский заголовок `shop_id` сам по себе не даёт прав.
- **PostgreSQL (Database-per-Service).** В Compose пять отдельных изолированных контейнеров PostgreSQL с собственными постоянными volumes:
  - `auth-db` (`auth_db`)
  - `merchant-dev-db` (`merchant_dev_db`)
  - `payments-db` (`payments_db`)
  - `notifications-db` (`notifications_db`)
  - `receipts-db` (`receipts_db`)
  Для каждой БД настрой отдельные роли владельца, миграции и исполнения, минимальные права и ограничение подключения. Сервисы физически и логически изолированы на уровне БД и читают чужие данные только через API или события. Начальные роли, БД и миграции создаются повторяемым способом.
- **Kafka.** Один брокер KRaft с volume в локальном профиле. Создавай топики явно. Пропиши стабильные идентификаторы consumer groups из раздела 5 в конфигурации потребителей. Для локального запуска используй коэффициент репликации 1, в том числе для топика offsets. Опиши отдельную конфигурацию для пилота с TLS, ACL, репликацией и мониторингом, без внешнего развёртывания.
- **Redis.** Подключи Notifications и используй Redis в демо для короткого лимита на отправку по магазину или адресу получателя. При потере Redis долговечные задания и история остаются в PostgreSQL. Явно обработай недоступность лимитера, например отложи отправку до восстановления. Redis доступен по приватной сети.
- **Локальные зависимости.** Добавь симулятор провайдера, SMTP-приёмник и получатель webhook. Получатель должен уметь вернуть временную ошибку и затем подтвердить доставку. Пропиши адреса и способ просмотра полученных сообщений. Демо webhook направляй на заранее заданный разрешённый локальный адрес. Регистрация произвольных URL для внешней среды требует проверки адреса и политики исходящего трафика.
- **Эксплуатация.** Добавь health endpoints для сервисов и проверки готовности инфраструктуры. Сохраняй ID корреляции через HTTP и Kafka. Используй структурированные логи. Для демо достаточно локального вывода, для пилота опиши сбор метрик Kafka lag, возраста outbox, зависших платежей и ошибок доставки. Закрепи версии образов. Все ключи, пароли, адреса и секреты получай из `.env`, в Git положи только `.env.example` с локальными значениями.

## 4. Базы, доступ и RLS

| Инстанс / База | Минимальные сущности |
| --- | --- |
| `auth-db` / `auth_db` | Аккаунты, сессии или refresh-токены. Глобальная модель идентичности. |
| `merchant-dev-db` / `merchant_dev_db` | Магазины, членство, роли, идентификатор и проверочный хеш API-ключа. |
| `payments-db` / `payments_db` | Платежи, попытки, ключи идемпотентности, ссылки checkout, сопоставление внешних ID, inbox, outbox. |
| `notifications-db` / `notifications_db` | Подписки, защищённые секреты подписи, inbox, задания, попытки и журнал доставки. |
| `receipts-db` / `receipts_db` | Inbox, демонстрационные квитанции, задания отправки, статус отправки. |

Храни `shop_id UUID NOT NULL` в записях магазина. Включи `ENABLE ROW LEVEL SECURITY` и `FORCE ROW LEVEL SECURITY` для платёжных таблиц и магазинных таблиц, доступных через Developer API, Notifications или Receipts. Используй `USING` и `WITH CHECK` с предикатом `shop_id = NULLIF(current_setting('app.shop_id', true), '')::uuid`. Задавай проверенный `shop_id` параметризованным вызовом `set_config('app.shop_id', ..., true)` в той же транзакции и на том же соединении. Глобальные аккаунты Auth защищаются правами Auth и проверками личности.

У рабочих ролей нет прав владельца таблиц, `SUPERUSER` или `BYPASSRLS`. Для проверки API-ключа, получения контекста по токену checkout, сопоставления callback провайдера и выбора фоновых заданий предоставь узкие операции доступа. Бизнес-запись после поиска выполняется под контекстом найденного магазина. Свяжи попытку с платежом по составному FK `(shop_id, payment_id)`. Для идемпотентности используй уникальность `(shop_id, operation, idempotency_key)`. Контроль доступа проверяй под рабочими ролями PostgreSQL.

## 5. Kafka и доставка

| Топик | Producer | Consumer group |
| --- | --- | --- |
| `dobropay.provider-events.v1` | Payments, outbox входящего контура | `payments-provider-events-v1` |
| `dobropay.payment-events.v1` | Payments, outbox бизнес-событий | `notifications-payment-events-v1` и `receipts-payment-events-v1` |
| `dobropay.dlq.<consumer>.v1` | Соответствующий обработчик | Инструмент диагностики и контролируемого повтора |

Используй `payment_id` как ключ партиции. Конверт содержит `event_id`, `event_type`, `schema_version`, `occurred_at`, `shop_id`, `payment_id`, `correlation_id` и минимальный payload. Документируй схему каждого события. Исключи карточные реквизиты, секреты, токены checkout и контакт покупателя из топиков. В демо Receipts получает синтетический адрес из локальной конфигурации. Дальнейший обмен контактами опиши отдельным авторизованным контрактом.

Публикуй из outbox после фиксации операции. Подтверждай offset после сохранения в inbox и создания следующего состояния или долговечного задания. Повторы по `event_id` не дублируют бизнес-операцию. Переходы платежа защищены от устаревших событий. Для webhook веди отдельную очередь в PostgreSQL, сохраняй результат доставки, ограничивай число попыток и повторяй с прежним `event_id`. Подписывай timestamp и исходные байты тела через HMAC-SHA256. Для SMTP с неопределённым исходом фиксируй отдельный статус, чтобы избежать автоматического дублирования письма при неподтверждённой отправке.

## 6. Сквозной сценарий

1. Подними сервисы и создай два демо-магазина. Сотрудник входит через Auth. Developer API позволяет ему выпустить серверный ключ и настроить тестовый webhook для своего магазина.
2. `POST /v1/payments` принимает API-ключ, `Idempotency-Key`, сумму целым числом в копейках и валюту RUB. Payments сохраняет платёж `pending` и ключ идемпотентности до выдачи `id`, `status` и `checkout_url`. Повтор с тем же ключом и телом возвращает тот же платёж, повтор с другим телом даёт `409`. `GET /v1/payments/{id}` доступен владельцу, для чужого и отсутствующего ID ответ одинаковый.
3. Покупатель открывает ограниченную по сроку checkout-ссылку. Явное действие запускает попытку и редирект к симулятору. Повтор использует тот же ключ попытки, пока исход неизвестен. Checkout показывает магазин, сумму и статус. Симулятор предлагает успех и отмену и присылает аутентифицированный серверный callback. Возврат браузера отображает статус.
4. Payments проверяет callback, сохраняет его до ответа и публикует нормализованное событие через outbox. Обработчик Kafka сверяет связь с попыткой, аккаунт провайдера, сумму и валюту. В одной транзакции сохраняет результат обработки, переход `pending → succeeded/canceled` и новое событие для магазина.
5. Notifications доставляет подписанный webhook в тестовый приёмник. Receipts при успехе сохраняет квитанцию и вызывает Email. Email отправляет письмо в SMTP-приёмник. Merchant Admin API показывает фактический статус из Payments. Отдельно продемонстрируй результат, когда покупатель закрывает вкладку после отправки оплаты.

## 8. Приёмка

- С чистого окружения по README запускаются семь независимых сервисов, Kafka, Redis, пять изолированных инстансов PostgreSQL (DB-per-Service), Gateway и локальные симуляторы. Миграции и настройка Kafka воспроизводимы.
- Сквозной сценарий проходит через реальные локальные HTTP-вызовы и Kafka. Видны платёж в кабинете, подписанное уведомление и письмо. Отмена отражается в API и кабинете, событие отмены доставляется магазину, квитанция об успешной оплате для отменённого платежа не создаётся.
- Два параллельных запроса с одним ключом создания дают один платёж. Повтор callback и Kafka-сообщения не дублирует переход или задание. Терминальное состояние не откатывается.
- Магазин A не видит и не меняет данные B через API или SQL под рабочей ролью. Запрос без контекста после завершения транзакции на том же соединении не видит строк магазина. Сервис не может подключиться к чужой БД.
- После остановки Kafka платежи и принятые callback остаются в PostgreSQL. После восстановления брокера сохранённый outbox обрабатывается. После сбоя webhook повтор приходит с тем же `event_id`. После восстановления Redis доставка продолжает работать с сохранённой историей.
- Прогони сборку, релевантные тесты и демо. В репозитории не должно оставаться временных файлов и ИИ-артефактов.
