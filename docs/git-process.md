# Git-процесс Dobropay

Этот документ обязателен для агентов. До изменения индекса, создания коммита, переключения ветки или иной Git-операции прочитай `AGENTS.md`, этот файл и проверь `git status --short --branch`. Существующие изменения другого автора не исправляй, не удаляй и не включай в свой коммит без явного поручения.

## Репозиторий и размер коммита

- Основная ветка — `main`. Каждую фичу веди в отдельной ветке; не коммить её напрямую в `main`. После каждого коммита сразу пушь ветку.
- После полного завершения фичи и успешного прохождения проверок (сборка без предупреждений и прогон всех тестов) агент **обязан самостоятельно смержить ветку фичи в `main`** и запушить `main` в удалённый репозиторий.
- Коммит создаётся **после каждого завершённого небольшого пласта изменений**: модуля, слоя, документации или конфигурации. Не копи несколько пластов в один коммит.
- Ориентир размера — до 10–15 файлов или одно значимое изменение. Микрофичу коммить отдельно, когда она завершена и проверена.
- Добавляй файлы в индекс явно. Перед коммитом просматривай `git diff --cached --stat`, `git diff --cached` и `git diff --cached --check`.

## Сообщения и авторство

Используй Conventional Commits: `<type>(<scope>): <короткое действие>`. Scope — имя модуля или слоя, например `payments`, `checkout`, `notifications`, `db`, `local`, `docs`.

| Тип | Когда |
| --- | --- |
| `feat` | Новая функциональность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение без смены поведения |
| `test` | Тесты |
| `docs` | Документация |
| `chore` | Инфраструктура, конфиги, зависимости |

Примеры: `feat(payments): add idempotent creation`, `fix(inbox): retry unresolved attempt`, `docs(git): record commit rules`. Сообщение короткое и по делу, без маркетинговых формулировок.

Автор и коммиттер — владелец репозитория. Пользуйся настроенными для репозитория `git config user.name` и `git config user.email`; не подменяй их агентом или инструментом. Не добавляй `Co-Authored-By`, подписи инструментов и сгенерированные приписки в коммитах и PR.

## Проверки и самостоятельный мерж в `main`

Перед завершением фичи и мержем в `main` выполни обязательные проверки:

```bash
dotnet build Dobropay.slnx -warnaserror
dotnet test Dobropay.slnx --no-build
git diff --cached --check
git diff --cached
```

Для отдельных промежуточных коммитов в ветке фичи запускать тесты не обязательно, но перед каждым коммитом проверяй `git diff --cached` на отсутствие реальных ключей, токенов, паролей и других секретов. Безопасные демо-значения допустимы в `*.example` и примерах документации, если они явно локальные.

Когда фича полностью реализована, рабочее дерево чистое (`git status --short`), сборка проходит без предупреждений, а все тесты зелёные — **агент самостоятельно мержит ветку фичи в `main` и пушит изменения**:

```bash
git checkout main
git merge --no-ff <feature-branch> -m "merge: <feature-branch> into main"
git push Origin main
```

Если проверка перед мержем падает, сначала исправь причину в ветке фичи, закоммить и запушь исправление, и только после успешного прогона мержи в `main`.

## Что не коммитится

Правила закреплены в `.gitignore`: `.env`, `.env.*` кроме `*.example`; `*.session`, `sessions/`; `.idea/`, `.vs/`, `.vscode/`; `bin/`, `obj/`, `TestResults/`; локальные базы и логи. Перед коммитом всё равно проверь индекс: `.gitignore` не удаляет уже отслеживаемые файлы и не защищает от случайного добавления секрета в другой файл.
